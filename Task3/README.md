

|**№**|**Действующие лица или системы**|**Use Case**|**Описание**|
| :-: | :- | :- | :- |
| 1 | Клиент | Просмотр списка депозитов | Клиент видит список доступных депозитов с актуальными ставками в интернет-банке и на сайте. |
| 2 | Клиент | Подача заявки на депозит | Клиент заполняет заявку на открытие депозита, указывая сумму и счет. |
| 3 | Кол-центр | Обработка заявки нового клиента | Менеджер звонит клиенту после подачи заявки через сайт и может предложить индивидуальные условия. |
| 4 | Бэк-офис | Подтверждение депозита | Менеджер в бэк-офисе подтверждает ставку и открывает депозит в АБС. |

| 6 | Клиент | Получение СМС-уведомления | Клиент получает уведомление о подтверждении депозита. |

### **Нефункциональные требования**

|**№**|**Требование**|
| :-: | :- |
| 1 | Доступность 99,9% и работа 24/7 |
| 2 | Система должна поддерживать горизонтальное масштабирование |
| 3 | Данные должны передаваться по защищённым каналам |
| 4 | Использование MS SQL и Oracle для совместимости с текущими системами |
| 5 | Возможность интеграции с Kafka (на перспективу) |
| 6 | Максимально быстрый отклик интерфейса |

### **Решение**
Приведены диаграммы контекста и контейнеров в модели C4.

#### **Диаграмма контекста**
1. Клиент взаимодействует с интернет-банком и сайтом.
2. Сайт передает заявки в систему кол-центра.
3. Кол-центр обрабатывает заявки и передает их в АБС через бэк-офис.
4. АБС хранит данные и управляет депозитами.
5. Клиент получает СМС-уведомления.

#### **Диаграмма контейнеров**
- **Интернет-банк** (Web-приложение) → API → База данных.
- **Сайт** → API → Система управления заявками (CRM).
- **Кол-центр** → CRM → API → АБС.
- **АБС** → Хранилище ставок (MS SQL / Oracle) → API → Бэк-офис.
- **СМС-сервис** → Клиент.

Архитектурные решения:
- **Выбрана микросервисная архитектура** для интернет-банка, чтобы упростить масштабирование.
- **Используется шифрование трафика** для защиты данных клиентов.
- **Отказ от прямого API-взаимодействия интернет-банка с АБС**, чтобы избежать перегрузки базы данных.
- **Распределение нагрузки** между серверами и дата-центрами.

---

### **Альтернативы**
1. **Прямое подключение интернет-банка к АБС**
   - **Плюсы:** Простота реализации
   - **Минусы:** Высокая нагрузка на АБС, сложность масштабирования

2. **Использование Kafka для передачи заявок**
   - **Плюсы:** Масштабируемость, надёжность
   - **Минусы:** Требует обновления платформы интернет-банка

3. **Использование кэширования ставок депозитов**
   - **Плюсы:** Снижение нагрузки на АБС
   - **Минусы:** Возможность устаревших данных

---

### **Недостатки, ограничения, риски**
- **Перегрузка базы АБС** – требуется дополнительное кеширование и отказоустойчивость.
- **Требуется шифрование данных** – без него передача данных будет уязвима.
- **Совместимость с текущими технологиями** – необходимо учитывать ограничения текущей платформы.
- **Масштабируемость интернет-банка** – требует доработки для поддержки больших нагрузок.
